# Whims

Ideas too small or too vague to be an item. One or two lines each, with no difficulty, area or plan.
A whim that grows a shape is promoted to an item file and its line is removed; deleting one is free.

| Slug | Whim |
| --- | --- |
| `whim-lsp-for-the-editor` | Language Server Protocol support for the editor: publish the C# compile diagnostics and the script checker's JavaScript diagnostics to [`editor-is-a-textarea`](editor-is-a-textarea.md)'s editor over LSP. |
| `whim-backlog-on-the-site` | The backlog is not on the site: `docs/backlog` and `docs/plans` live in the repository, and the assistant reads the page store, so it cannot see what is already queued and proposes work that is already an item or a plan. A `/backlog` page — the item list rendered from those files by the build and seeded like any other, or written by hand and kept honest — would let the assistant ask "is this already known?" and let the owner share the list with it. |
| `whim-build-timings` | The build reports no timings: `dotnet format`, `make check`, each test suite, `make image` and the ssh deploy steps are measured only by whoever watches the terminal. Record each duration during the build and push it as a JSON blob to an endpoint that updates the site's Prometheus metrics, so the trends are visible on `/status`. |
| `whim-mcp-server-tools` | The assistant cannot reach a tool it does not hold: `ToolRegistry` is a closed list of compiled-in types, so a capability that belongs in another process — a mailbox over IMAP, a calendar, someone else's API — can only become more host code. Make the assistant an **MCP client**: configured servers whose tools are discovered at run time and sit beside the static ones in the registry, each call approval-gated and each result untrusted data like a fetched body, with the server list a policy value. The first server is the mailbox — [the email plan](../plans/email.md)'s Dovecot over IMAP, in its own process rather than in the host. |
| `whim-page-file-upload` | A page cannot take a file: `PageRequest` carries query, form, headers and cookies as text, which is half of why the archive stays in the shell ([keel](../spikes/keel.md)). Add `Files` — a read-only list of parts, each with the client's file name, the claimed content type, the host's measured size and a forward-only stream over the bytes — with the shell spooling every part to a temp root before the render starts, so the upload is not paid out of the render deadline, and deleting the spool when the render ends, abandoned or not. The cap is a policy value, 1 GB per request shipped and counted on the bytes actually written rather than a header's claim, a part that outruns it is a `413` naming the limit, and the name and type are claims the page treats as data rather than authority. |
| `whim-page-file-download` | A page cannot give bytes out: `IPageResponse` writes strings and every body is buffered against `Pages:Render:MaxBodyChars`, so an archive, an image or a generated file can only leave as base64 inside HTML — the other half of the archive's blocker. Give a page a binary body that can **only** be streamed: the bytes are written after `FlushAsync` has committed the response, so the render slot becomes a stream slot and the existing clocks bound it (`Pages:Stream:SilenceSeconds`, `MaxSeconds` and `Slots`) rather than a byte cap, while a buffered text body keeps the cap it has. `Content-Disposition` joins the header allow-list, or a `Download(fileName)` member owns both it and the content type, with the file name escaped and never taken from the request. |
| `whim-a-worker-waits-for-a-message` | A worker cannot block on the durable queue: [`IMessageStore`](../../src/uk.osric.asp.Sdk/IMessageStore.cs) is peek-and-take only, because a render answers a visitor and must not wait, and `IWorkerContext.ReceiveAsync` waits on the job's in-memory channel rather than on `StoreMessages`, so a worker waiting for a topic polls `TakeAsync` and uses a timed `ReceiveAsync` to keep its silence clock armed. Give the job a wait on the store — `WaitAsync(topic, waitSeconds)`, bounded by `Pages:Jobs:MaxWaitSeconds` and pausing the silence clock the way `ReceiveAsync` does — implemented as a bounded poll in the store or by waking it through the job's channel; a page render still never waits. Revisit the next time background workers come up, and edit `pages-a-message-is-taken-once`, which records that there is no wait. |
